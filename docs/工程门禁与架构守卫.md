# 盘古工程门禁与架构守卫

状态：G00 已实现；G01/G02 的模块、编译、符号、静态 ELF 和服务组合候选探针已有拒绝测试。完整生产准入、ABI/运行时验证和外部受保护执行器尚未完成，不能以局部探针通过代替放行。

## 当前适用范围（2026-10-24）

本规范的 G00～G11 是分阶段质量目标，不是本地开发前必须全部建设完毕的项目。当前优先交付原生最小 Agent 与 TUI，实施顺序以迁移 TODO 的近期执行队列为准；下文的“正式放行”“受保护执行器”指受保护主线/发布保证，不作为所有本地实现的前置要求。

当前必做：文件及模块/依赖登记；可重复构建；宿主不混入模型/UI业务、服务不越过私有实现；受影响的行为、内存、生命周期测试；工具执行的工作目录、权限、取消与输出上限；凭据不入库、不进入日志。必要替换点使用最小替身验证即可，默认静态组合允许先交付。

首个核心批次补齐所用模块与构建登记和直接边界检查，随后随功能增量维护。不得为通过现有失败测试降低规则，也不以任意未实现的未来门禁阻断无关功能。只有实际触及 ABI、持久化、权限等风险时才执行相应专项。全平台、动态加载、完整兼容、完整性能预算和远端防绕过建设放到相应功能或发布阶段。

每次交付只需一份简短记录：变更、相关检查结果、已知限制、下一项。已有证据可以引用，不反复生成同义报告，不追求测试数量增长。控制面自审保留摘要和结论，日常函数/helper不额外审批。

## 1. 目标与保证边界

工程规则必须转化为可执行检查：说明禁止什么、从哪里采集证据、如何失败、如何验证检查本身。Agent 的自述、文档中的承诺和一次模型审查均不作为放行证据。

门禁用于阻止已知的架构违规、资源失控、接口破坏和可测量回退。它不能证明设计永远正确，也不能自动判断所有抽象是否必要。无法可靠自动判断的设计变更必须有显式设计审查；根据用户 2026-10-20 的决定，允许 Agent 自审自批，须如实记录审查者与实施者是否同一身份，不得伪装成独立审核或机器已经证明。

本规范约束项目代码、构建、测试与交付。`references/` 是不进入产品的上游参考材料（用户授权 Pi/Harness 干净快进更新，禁止编辑其源码），不进入产品构建、扫描基线、发布物和默认依赖。不得通过复制第三方代码到参考目录再参与构建来绕过规则。

## 2. 权威与防绕过

执行顺序：用户明确决定 → 已批准的项目架构与控制配置 → 模块接口 → 实现。Agent 不得为了使自己的实现通过而同步放宽检查。

控制面包括：门禁脚本、模块清单、依赖规则、预算、参考基线、豁免、构建入口、CI 配置及分支保护设置。控制面变更与业务变更分别审查；即使同一次提交中修改，也必须单独记录控制面差异、固定摘要及审查批准结论。用户已授权 Agent 自审自批，无须逐包等待用户确认；不得为迁就实现而放宽门禁、预算、测试或基线。

正式放行要求：

1. 必需 CI 和分支规则在服务器侧配置，普通编码 Agent 无修改权限；本地 hook 只是快速反馈。
2. 外部受信任执行器从受保护版本加载门禁及规则，检查待审源码。不得只执行待审分支自己提供的检查器。
3. 控制面更新先完成记录在案的审查批准和相应门禁自测；Agent 可按用户授权自审自批。受保护版本的生效仍须由实际部署、权限与服务器回读证明，文档批准不自动改变远端配置。候选分支上的新规则结果可供预览，不能取代旧规则结果。
4. 验证回执绑定源码内容摘要、策略版本、工具链、构建参数及产物摘要；修改源码后旧回执失效。检查器崩溃、超时、未知模块、缺失必需检查一律不放行。
5. 参考源码、控制面和产品源码的变更范围分别列出；不得伪造报告、删掉失败用例、降低预算或隐藏告警以通过检查。

当前已初始化本地 Git，并按用户要求创建公开仓库 `xu-yuanhao/PanGu`。按用户本轮决定，远端采用单 main 开发：保留禁止强推/删除，取消旧的强制独立 PR 审批与尚未部署的必需状态检查；对应 `pangu.github-development.v2` 只验证开发配置，不授予生产放行。引导与实验分支已有提交，源码与本地实验记录已持续公开推送；这不表示受保护主线已获得生产放行。外部受保护执行器、状态检查发布者绑定和独立审批尚未部署，当前自动化凭据仍有仓库管理权限。本地 G00 和远端配置回读均不能据此证明普通编码权限无法修改保护规则，故不宣称已有不可绕过的门禁。

## 3. 架构与代码准入

### 3.1 模块清单

每个生产代码文件必须属于一个登记模块；每个模块登记以下信息：

- ID、角色、源码根、责任与明确非职责。
- 公开头文件、导出符号、服务 ID/版本、提供者与消费者。
- 允许的直接依赖、第三方依赖、目标平台与架构。
- 静态/动态交付方式、默认组合、激活条件。
- 状态与资源所有者、线程/回调规则、清理入口。
- 体积、常驻内存及相关关键路径预算。

清单不只是手写依赖图：检查器必须将其与编译输入、实际包含关系、链接依赖和运行时服务绑定交叉验证。清单声称没有依赖而链接产物中存在依赖，仍然失败。

### 3.2 固定边界

| 区域 | 可写内容 | 禁止内容 | 必需检查 |
|---|---|---|---|
| Bootstrap/Host | 引导、服务解析、资源归属、生命周期约束 | 模型厂商、Coding 业务、UI、数据库等具体实现 | 依赖/符号白名单、最小宿主链接检查 |
| 原生基础服务 | 分配、Buffer、解析、事件后端等默认实现 | 隐式绑定业务插件、未经声明的进程级状态 | 依赖图、导出符号、替换用例 |
| Runtime 服务 | Agent Loop、Session、Tools 等接口与插件实现 | 直接引用其他服务的私有实现、隐式选定提供者 | 私有头文件隔离、服务绑定检查 |
| 业务插件 | 服务提供者、工具、策略 | 绕过受控授权、直接访问其他插件内部状态 | 受控执行路径及替换测试 |
| PAL/平台实现 | 对应平台 API、系统调用与资源封装 | 业务策略、无声明的平台泄漏 | 目标平台编译、平台符号检查 |
| Client | 输入、显示、协议适配与 UI 状态 | 私有 Agent Loop、独立业务会话真相 | 依赖/协议检查、多客户端一致性用例 |

服务定义包不能依赖其提供者。模块图不得有未批准的循环，不能通过“公共 utils”间接形成循环。接口内共享数据不等于允许共享可变全局状态。

低层实现可在构建或启动时选择，不强制热替换。插件既可静态注册也可动态加载，不能把“每个函数都做动态调用”当作插件化验收。

### 3.3 实现前的参考阅读

每个实现批次先读固定参考中对应函数、直接调用和相关测试，再决定原生实现。Pi Durable定义主要行为与提交/恢复语义，旧Coding Agent仅辅助；Harness/Cordis提供组合/生命周期；平台ABI与库调用以实际接口规范为准。模块登记中的reference_basis仅提供可定位入口，不等于“已经读过”。读取结果简短写入现有进展/交接：提交、路径/函数、采用语义、有意差异与验证；无对应参考则明确说明理由，不能凭经验伪称兼容。

本地检查可以验证来源信息/文件/行为，无法可靠证明AI是否真正阅读理解。不能用勾选或多写阅读报告替代实际行为用例；不为这一要求新建通用审批/文档门禁。编译和产品运行不依赖references目录，避免把参考仓库变成产品依赖。

### 3.4 语言与依赖

语言顺序固定为Assembly第一、C第二、C++第三。Loop、Session、工具注册/状态、Buffer/文本及TUI输入/状态/渲染优先手写汇编；不能以“先完整C、最后按热点优化”代替此要求。C用于具体平台结构与成熟外部库的薄胶水，C++限明确批准的桥接。ABI是C约定不等于实现语言是C。

重构采用单版本原地替换：移植完成删除旧源、旧构建项/导出和失效登记，不把旧C搬进tests/legacy/reference，不添加双后端或fallback。回溯用Git历史。手写汇编壳跳回C核心、编译器生成的汇编文件均不构成完成。测试按原用例、Pi行为、ABI和边界执行，不保留整套旧产品代码作为测试预言机。

可执行范围：`governance/assembly-first.json`记录当前交互组合的语言职责；现存待替换C核心只登记内容摘要，防止迁移期间继续扩展，未复制源码。替换时在同批删除C、加入.S、更新清单和实际构建。`tools/gates/assembly_first.py`检查语言顺序、精确文件、待迁移C是否变动和桥接理由；主构建把实际SOURCES传入核对，G00也运行该检查。当前清单允许尚未完成替换的现状，不代表Assembly-first实现已验收。检查不证明汇编内部没有委托C或代码确为手写，这些由实现/链接审查确认；不设行数百分比配额。


原生Runtime核心优先手写Assembly，C限必要胶水；C++仅限明确批准的桥接，ABI 不暴露 C++ 类型和异常。TypeScript、Kotlin 等仅进入其登记的客户端或可选宿主。检查构建实际编译输入，不能只依据扩展名判断语言。

新增运行时依赖必须登记用途、版本/来源、许可证、传递依赖、体积和平台影响。禁止默认带入 Node.js、Python、JVM、浏览器或 GUI 框架到最小原生 Agent。开发期脚本使用 Python 等工具不等于产品运行时依赖，二者在依赖清单中分别记录。

系统调用与平台 API 限于登记的平台模块和必要引导代码。对 Assembly 检查指令、重定位及目标导入，对 C/C++ 检查编译与链接证据；文本关键字搜索只作快速预检，不能作为唯一证明。可信 Native 插件仍可直接调用 OS，因此这条规则是代码准入要求，不宣称能对任意机器码建立沙箱。

## 4. 同时防止臃肿与过度模块化

### 4.1 什么时候建立边界

新增独立服务或插件必须满足至少一个可检查的目的：

- 已有实际的多消费者或多个实现。
- 需要独立权限、执行位置、资源生命周期或交付/激活控制。
- 是主架构明确要求的替换点，例如 Agent Loop、Session、Allocator。

尚无第二个生产实现的必需替换点可使用最小测试提供者验证，不能为了凑数量制造两套生产实现。

新增普通内部 helper 不需逐次审批；只有扩大公开边界、新增服务/包、引入依赖或改变预算时，才进入结构变更审查。

### 4.2 允许直接实现

单模块内部允许直接函数调用、私有结构体、静态表和小型辅助函数。职责一致的代码可以共处一个文件。不得为了“可扩展”给所有函数加工厂、虚表、注册表、配置开关和跨模块消息。

### 4.3 机器阻断与审查分工

机器阻断：未登记模块/依赖/公开导出；越过私有头文件；循环依赖；最小组合带入禁用组件；独立目标无法构建；替换用例仍需修改宿主；模块数量、导出数量或预算增长未登记。

设计审查（允许 Agent 自审，必须记录结论）：只转发调用的层是否必要、抽象是否有实际消费者、公共工具是否混入多种职责、是否为假设需求提前建框架。检查器输出新增节点、边、导出、文件及调用转发的差异；Agent 可以按用户授权签发设计审查结论，但不能以此替代可执行检查或声称具有独立审查保证。

不设“文件不得超过 N 行”“函数只能调用 N 层”“每层只能依赖下一层”等全局硬阈值。它们会鼓励拆文件和机械间接层，不能代表模块化质量。复杂度指标用于定位审查，只有经模块实测验证的局部预算才允许阻断。

以下为目标检查。除 G00 外均未完成完整生产准入；已实现的局部候选探针详见 T05 实施记录。当阶段需要某项时，必须先实现检查再进入该阶段，不能将未实现输出为 PASS。

| G01 架构依赖 | 越界依赖、私有实现泄漏、循环、宿主带业务 | 编译依赖、链接图、服务图、禁止边规则 | 第一份生产代码前 |

| G07 内存与并发 | 越界、UAF、泄漏、竞态或无界增长用例失败 | 可用 sanitizer、guard page、分配器探针、压力用例 | 分配器与异步服务前 |
| G08 安全与执行 | 拒绝仍执行、跨作用域越权、沙箱静默降级、凭据泄漏 | 真实执行拒绝用例、隔离后端能力检查、日志检查 | 文件/Shell/凭据接入前 |
| G09 产物与依赖 | 超体积/依赖预算、禁止组件、可选能力进入最小包 | 实际发布包、链接 map、导入表、SBOM/依赖清单 | 首个最小可执行产物前 |
| G10 性能与资源 | 经确认的回退或绝对上限超额 | 受控基准、分配计数、队列上限、RSS 与启动测量 | 首条可测关键路径起 |
| G11 交付完整性 | 必需检查缺失、摘要不符、回执过期或最终产物未检查 | 受信任执行器汇总与产物摘要 | 首个合并/发布流程前 |

每个检查必须提供合法样例与故意违规样例，证明它会阻断；检查器自身的测试在控制面修改时必须执行。

## 6. 性能与体积预算

### 6.1 预算先登记，基线后测量

按具体 Profile、平台、架构和构建模式登记指标。最低包括：宿主体积、最小 Agent 部署体积、冷启动、Idle/峰值 RSS、每次工具分发的分配次数、插件激活、队列与 Buffer 上限；JSON/搜索等热点各自登记吞吐、延迟与输入规模。

数值由首个可运行实现和明确资源目标确定，不在无实现阶段编造微秒、KB 或百分比。没有已批准预算的目标标记 `UNBASELINED`，不能当作性能验收通过。最小部署体积计入必需插件、TLS 与随包依赖；静态和动态两种交付不可使用不同统计口径规避预算。

### 6.2 测量规则

- 固定编译器、链接参数、硬件/OS、CPU 能力、输入语料和缓存条件，记录环境元数据。
- 基准阶段不访问真实模型或公网；网络用本地可控服务，外部等待与框架成本分开测量。
- 指标同时设绝对资源上限和适用的相对回退规则，使用预热、重复采样与稳定统计量。
- 差异处于噪声区间则重测并报告不确定性，不能选最好的一次；重测次数有上限，环境不稳定进入阻塞状态，不伪造通过。
- 关键性能检查在专用执行环境完成；普通 CI 的抖动结果不能直接证明微秒级回退。
- 超预算须修复，或经单独记录的控制面审查修改目标；不得在同一实现变更中静默更新基线。

可复现的结构性上限优先硬检查，例如最大队列长度、最大并发、输入长度限制和单操作分配计数。SIMD、零复制和汇编优化必须通过正确性对照及实际收益证明；不能以技术标签替代数据。

## 7. 原生代码的必需验证

接口与资源：长度/容量溢出、边界输入、UTF-8/JSON 错误、借用/转移、跨分配器释放、取消与完成竞争、回调线程与重入、初始化一半失败、消费者先于提供者退出。

Assembly：调用约定、栈对齐、callee-saved 寄存器、结构布局、CPU 指令支持检测及回退路径；用受控输入和参考实现进行差分测试。

Sanitizer 不能完整覆盖手写汇编访存。需要 guard page、红区/哨兵、分配器资源计数和边界语料等补充手段。不能因 sanitizer 未报错就宣布汇编内存安全。

并发与流：慢消费者、断线、乱序完成、部分输出、超时与连续取消；验证队列/内存有界，最终结果不丢失。不可撤销的外部副作用要有明确完成语义，禁止盲目重试。

测试按风险选择；不要求机械的 100% 行覆盖率，不为可逆的小文案修改堆测试。ABI、内存、生命周期、安全与状态恢复属于必测行为。

## 8. 变更流程

1. 编码前确定受影响模块、允许依赖、接口和验收用例；普通实现选择在已批准边界内自主进行。
2. 新增模块/服务、改变依赖、语言、ABI、状态格式、权限或预算时，先记录结构差异和相应自审结论再实施；用户已授权 Agent 自审自批，无需重复确认。
3. 先跑快速静态检查，再运行受影响模块测试与构建；提交候选结果时执行所有适用必需检查。
4. 定时全量检查与发布矩阵补充增量检查盲区；发布前对最终产物重新核验，不复用别的构建回执。
5. 完成报告列实际执行命令、结果、未实现/不适用项及原因。不得将“计划有测试”写成“测试通过”。

门禁状态统一为 `PASS`、`FAIL`、`BLOCKED`、`NOT_APPLICABLE`。`NOT_APPLICABLE` 必须由受保护阶段规则判断，不能由提交者随意填写；必需检查未实现、环境不可用或超时为 `BLOCKED`。

## 9. 例外与技术债

禁止永久通配豁免。每条例外绑定规则 ID、精确对象、原因、补偿措施、维护者批准、到期条件及跟踪项；检查器验证例外未过期且范围未扩大。

原生内存安全、执行授权和回执真实性的失败不能通过普通预算豁免变成通过。必要的设计变更须修改接口或实现并重新验证。

不要用 TODO、兼容分支或隐式 fallback 掩盖缺失服务和不支持的平台。兼容层只有在有明确支持对象、行为测试和删除条件时才能加入。
